# Build Job Radar — V1

Build a full-stack web application called **Job Radar**.

## 1. Product Goal

Job Radar is a personal job-monitoring platform that automatically monitors **manually configured company career pages and public job APIs**, discovers newly posted jobs, evaluates them against a user-defined job profile using a **transparent rule-based matching engine**, and sends an email notification when a new job meets the configured match threshold.

### Critical V1 requirement

**V1 must NOT use AI/LLMs/embeddings.**

However, the application architecture must be deliberately designed so that an AI-based matching engine can be added later **without restructuring the rest of the application**.

The core architecture should therefore separate:

```text
Job Sources
    ↓
Fetching
    ↓
Normalization
    ↓
Persistence
    ↓
Filtering
    ↓
Matching Engine
    ↓
Notification
```

The matching layer must be accessed through a clean abstraction such as:

```text
IMatchingEngine
```

with the V1 implementation:

```text
RuleBasedMatcher
```

Later, an implementation such as:

```text
AIJobMatcher
```

should be able to replace `RuleBasedMatcher` without requiring changes to job fetching, database, dashboard, notification, or source management code.

---

# 2. Technology

Use a modern, maintainable full-stack TypeScript architecture unless there is a strong technical reason to choose otherwise.

Preferred stack:

* **Frontend:** React + TypeScript
* **Backend:** Node.js + TypeScript
* **API:** REST
* **Database:** PostgreSQL
* **ORM:** Prisma or another well-supported TypeScript ORM
* **Styling:** modern responsive component-based UI
* **Validation:** Zod or equivalent
* **Email:** provider abstraction with a simple SMTP-compatible implementation for V1
* **Scheduler:** background scheduled process running approximately every hour
* **Testing:** unit tests for matching and source normalization

Keep the architecture modular.

Do NOT introduce microservices, Kubernetes, message queues, or other infrastructure unless genuinely necessary for V1.

The goal is a reliable modular monolith that can later be split if required.

# 3. Application Architecture

Use clear separation between:

```text
Frontend
    ↓
REST API
    ↓
Application Services
    ↓
Domain / Matching
    ↓
Repositories
    ↓
PostgreSQL
```

Job ingestion should be separated into source adapters:

```text
JobSource
├── GreenhouseSource
├── LeverSource
├── StructuredCareerPageSource
└── GenericHttpHtmlSource
```

The system should not assume every website can be scraped.

Only support publicly accessible sources where automated access is permitted.

Do NOT:

* bypass authentication
* bypass CAPTCHAs
* bypass anti-bot systems
* access private APIs
* reverse engineer private/internal APIs
* evade robots/access restrictions

If a source cannot be safely or reliably accessed, mark it as unsupported/failed and show the reason in the source status.

# 7. Scheduler

Implement a scheduled background process that runs approximately **once per hour**.

The scheduler should:

1. Find enabled sources.
2. Fetch jobs.
3. Normalize jobs.
4. Upsert jobs into the database.
5. Identify newly discovered jobs.
6. Run the matching engine against relevant new jobs.
7. Store match results.
8. Send notifications for jobs above the configured threshold.
9. Record notification history.
10. Record source success/failure information.

Make the scheduler runnable locally.

Provide clear README instructions such as:

```text
npm run scheduler
```

or the equivalent for the selected architecture.

Also provide a way to manually trigger a source/job scan from the UI for development/testing.

Do not require the scheduler to run continuously during development if a manual trigger is available.

Create a clean interface:

```text

```

```text

```

The rest of the application must depend on the interface rather than directly depending on `RuleBasedMatcher`.

The matcher should return a structured result such as:


# 10. V1 Matching Rules

Implement scoring for:

### A. Role/title relevance

Compare the job title against preferred roles.

Example:

```text
"Full Stack Software Engineer"
```

should match:

```text
"Full Stack Developer"
"Software Engineer"
```

Use configurable keyword/phrase matching rather than AI semantic understanding.

### B. Skill matching

Compare configured skills/technologies against:

* title
* description
* requirements
* responsibilities
* other available job metadata

Calculate matched skills and missing skills where detectable.

### C. Experience compatibility

Attempt to detect phrases such as:

```text
2+ years
2-4 years
3 years required
minimum 2 years
```

Compare with the configured candidate experience.

If experience cannot be detected, do not assume a mismatch.

### D. Location compatibility

Compare job locations against preferred locations.

Handle:

* Remote
* Hybrid
* On-site
* multiple locations

### E. AI/GenAI relevance keywords

V1 should use only explicit keywords.

Examples:

```text
AI
GenAI
Generative AI
LLM
Azure OpenAI
OpenAI
Semantic Kernel
RAG
Agentic AI
Machine Learning
```

Do NOT use an AI model to determine relevance in V1.

### F. Freshness

Prefer recently posted jobs.

Make the freshness contribution configurable.

# 11. Configurable Scoring



# 19. Future AI Architecture

This is extremely important.

Do NOT implement AI in V1.

However, design the matching system so the future architecture can look like:

```text
IMatchingEngine
       │
       ├── RuleBasedMatcher
       │
       ├── AIJobMatcher
       │
       └── HybridMatcher
```

The rest of the application should call:

```text
matchingEngine.match(job, profile)
```

without knowing which implementation is being used.

Later, AIJobMatcher should be capable of using:

* LLMs
* embeddings
* semantic similarity
* skill equivalence
* role relevance
* missing skill detection
* explanations
* job ranking

Potential future providers include:

```text
Azure OpenAI
Gemini
Groq
Mistral
GitHub Models
OpenAI-compatible APIs
```

Do not hardcode any provider.

Future provider credentials must be stored through environment variables/configuration.

The architecture should allow something like:

```text
AIProvider
├── AzureOpenAIProvider
├── GeminiProvider
├── GroqProvider
├── MistralProvider
└── OpenAICompatibleProvider
```

without changing the Job entity, source system, notification system, or dashboard.

# 28. Implementation Strategy

**Do not attempt to generate every feature at once if doing so would reduce reliability.**

Build the application incrementally in this order:

### Phase 1

Project structure + database + basic UI + API.

### Phase 2

Companies + sources + jobs.

### Phase 3

Greenhouse/Lever/public source ingestion + normalization + deduplication.

### Phase 4

Candidate profile + rule-based matching.

### Phase 5

Dashboard + job search/details.

### Phase 6

Email notification + notification history.

### Phase 7

Scheduler + retries + source health + logging.

### Phase 8

Testing + documentation + deployment configuration.

After each phase, keep the application runnable.

Do not replace working functionality with mock implementations once real functionality has been implemented.

---

## Final instruction to the coding agent

Before writing large amounts of code, establish the project structure and database/domain model.

Keep the code modular, readable, and understandable to a developer who will continue building the project manually.

**The most important architectural requirement is that fetching, normalization, persistence, matching, notification, and future AI functionality remain loosely coupled.**

V1 must be completely functional **without AI**.

The future goal is:

```text
V1

Job Sources
    ↓
Normalized Jobs
    ↓
RuleBasedMatcher
    ↓
Notifications


V2

Job Sources
    ↓
Normalized Jobs
    ↓
IMatchingEngine
    ├── RuleBasedMatcher
    ├── AIJobMatcher
    └── HybridMatcher
            ↓
       Notifications
```

Build V1 with this future architecture in mind, but do not implement V2 AI functionality now.
